## 2. Независимые направления — критерии

1. **Три системные кнопки:** панель приложения не закрывает Back, Home, Recents, нижние элементы остаются доступными.
2. **Системные жесты:** отступ учитывает жестовую полоску и края свайпа, без искусственного пустого пространства.
3. **Статус-бар и вырез:** контент ниже часов, сети, батареи и выреза камеры, не рисуется поверх значков.
4. **Переключение навигации:** `WindowInsetsCompat` пересчитывает реальные отступы, в том числе после смены режима в настройках Android.
5. **Экраны:** маленькие, большие, вытянутые, вырезы, поворот, split-screen, изменение размера окна и клавиатура.
6. **API 24–37:** установка, запуск и все функции проверяются на каждой версии Android с нужными разрешениями.

## 3. Приёмочные тесты — для каждого Android

- Чистая установка, повторный запуск, разрешения на фото и видео, включая частичный доступ Android 14+.
- MediaStore: сканирование фото и видео, разные физические папки с одинаковыми названиями, изменение медиатеки.
- Сейф: зашифровать, удалить оригинал с подтверждением ОС, открыть, сменить PIN, восстановить без потери.
- Реклама: test ad в debug, разрешения UMP, смена согласия, отсутствие рекламы поверх меню/панелей.
- Статус-бар, 3 кнопки, жесты и смена навигации при запущенном приложении.
- Портрет/альбомная ориентация, вырез, 360/393/480dp и широкие экраны, split-screen, клавиатура.

## 4. Что уже проверено, а что нет

- Скрипт `scripts/check_android_compat.py` проверяет **конфигурацию** SDK, но не работоспособность на всех устройствах.
- GitHub Actions подтверждает текущую **компиляцию** APK с SDK 36, но не 14 тестов в эмуляторах. API 37 не считается проверенным.
- Совместимость Android 7–17 будет подтверждена только по результатам испытаний на версиях и разрешениях, а не по одним цифрам Gradle.

Документация: https://developer.android.com/about/versions/17/setup-sdk и https://developer.android.com/build/releases/agp-9-2-0-release-notes

## Тестирование Android APK на реальных эмуляторах

Добавлен отдельный workflow `.github/workflows/android-device-smoke.yml`. В первом запуске 31.10.2026 обе проверки завершились ошибкой настройки: `./gradlew: not found`, потому что шаг `cd android` выполнялся отдельной оболочкой. Исправлено запуском единого `scripts/run_android_emulator_tests.sh`. Это пока не подтверждает прохождение эмуляторов.

- При отправке изменений в рабочую ветку запускаются **Android 7.0 (API 24)** и **Android 16 (API 36)**. Они проверяют реальную установку и запуск APK, Android WindowInsets, видимость WebView и отсутствие полноэкранного скрытия статус-бара.
- Ручной запуск `workflow_dispatch` позволяет прогнать **все API 24–37**. API 37 считается экспериментальной целью до успешной установки соответствующего образа и выполнения испытаний.
- Скрипт `scripts/emulator_navigation_smoke.sh` дополнительно проверяет портретную/альбомную ориентацию, изменение разрешения окна и пытается переключить системные кнопки/жесты на Android 10+; неподдержанные производителем переключения отмечаются как пропущенные, а не как успешные.
- Успешная компиляция APK **не** считается успешным прохождением эмуляторов. Состояние смотри по отдельному workflow.

Манифест теперь не содержит ограничений `android.max_aspect` и `android.min_aspect`: адаптация под любые пропорции регулируется фактическим размером окна.

## 2026-11-01 — Исправление WebView Android 7

WebView эмулятора Android 7 не поддерживает нативные ES-модули Vite. Обычное понижение синтаксиса до ES2019 недостаточно: `<script type="module">` вообще не выполнится на старом движке. Для Android APK подключён `@vitejs/plugin-legacy` 8.2.3 с локальными SystemJS-чанками и полифилами (`renderModernChunks=false`), сохраняя веб-версию сайта без изменений. JS и полифилы включены в APK и не требуют интернета. CI отдельно проверяет наличие legacy-чанков и скриптов загрузки в `dist/client/index.html`. Результат подлежит подтверждению эмуляторными испытаниями Android 7.

## 2026-11-01 — Исправление загрузчика старых WebView
CI выявил, что Vite выпускает System.register чанки, но TanStack Start создаёт HTML вне стандартного HTML-конвейера плагина legacy. Поэтому полифиллы и загрузчик не попадали в `index.html`. Теперь `scripts/bootstrap_legacy_android.mjs` **до `cap sync android`** копирует локальные `core-js-bundle` и `SystemJS` в `dist/client/assets`, подключает их в порядке ES-полифиллы → SystemJS → legacy entry и удаляет module-only скрипты из Android HTML. Команда CI строго проверяет файлы и сам HTML. Приложение не скачивает эти зависимости во время работы. Требуется подтвердить фактический запуск на API 24.

## 2026-11-01 — Расширенные испытания навигации

- При каждом push тестируются Android API **24, 29, 33 и 36** (ранее только 24 и 36). Полный список 24–37 — отдельный ручной запуск, при этом API 37 остаётся непроверенным.
- В эмуляторах фиксируются WebView user-agent, код стартовой страницы, статус загрузчика JavaScript, наличие нижней панели, системные WindowInsets, снимок экрана и logcat. Артефакты доступны в GitHub Actions даже при ошибке.
- Нижняя панель получает отступ от Android через обычное свойство `paddingBottom`, чтобы корректно работать на старых WebView; высота панели не складывается с системной полосой второй раз.

## 2026-11-01 — Дополнительные исправления системной навигации и просмотрщиков
- Android instrumentation теперь проверяет именно Capacitor WebView (а не случайный рекламный или consent WebView), что исключает ложные `NOT_READY` из-за выбора неправильного web-компонента.
- Добавлен тест корректности границ статус-бара/навигации в реальном окне Android.
- Полноэкранный просмотр фото/видео и просмотр из Сейфа используют стандартные `calc(var(--app-safe-* ) + padding)` вместо `max(...)`, которого нет на старых WebView.
- Верхняя/нижняя панели фотографий обходят боковые вырезы, а нижняя панель может прокручиваться на узких и горизонтальных экранах.
- Инициализация native insets выполняется уже на уровне root-компонента, до перехода к остальному интерфейсу.

## Android 7–16: устранение ошибки запуска (01.11.2026)
В четырёх эмуляторах (API 24, 29, 33, 36) подтверждён одинаковый класс проблемы: в prerendered HTML TanStack Start оставались обычные `<script>` с ESM-`import` и другой неподходящей для старого WebView синтаксической конструкцией. Приложение выдавало `SyntaxError: Unexpected token {` либо `Cannot use import statement outside a module`. В Android-сборке теперь убираются лишние SSR-скрипты, сохраняется только ES5-обработчик ошибок, затем строго в порядке загружаются локальные core-js, SystemJS и legacy JS entry. CI проверяет ровно четыре script-тега и отсутствие классических ESM-скриптов. Пока эмуляторы не пройдут заново, совместимость не отмечается подтверждённой.

## 01.11.2026 — исправлен подход к браузерной совместимости
Логи всех четырёх эмуляторов (API 24/29/33/36) показали `Unexpected token {` или `Cannot use import statement outside a module` при смешивании обычных ESM-скриптов TanStack и принудительного SystemJS Vite 8. Реальный WebView Android 7 из CI — **Chromium 69**, где ESM уже поддерживается. Поэтому для мобильной сборки заменён принудительный SystemJS на нативный `<script type="module">`, с Vite target `chrome69` и встроенными (offline) core-js полифилами. CI дополнительно проверяет, что файл модуля существует, HTML содержит только ES5 обработчик ошибок, локальные полифилы и единственный модульный entry. Фактический запуск нуждается в повторном эмуляторном испытании.

## 01.11.2026 — Изоляция Android от серверного TanStack Start
На эмуляторах API 24,29,33,36 предыдущая сборка уже не давала синтаксических ошибок, но падала при SSR-инициализации с `Cannot set properties of undefined (setting 't')`. Принято архитектурное исправление: Android теперь использует собственный `vite.android.config.ts`, `android-index.html`, `src/android-client.tsx` с `createRoot + RouterProvider`, общие файлы маршрутов и CSS. Страницы TanStack Start и SSR/гидратация остаются только для веб-версии. Все JS/CSS, полифиллы и медиа-переходы собираются локально. Проверка `check_legacy_webview.py` проверяет отсутствие SSR, наличие одного клиентского entry и офлайн-полифиллов. Поддержка Android 7–17 остаётся требованием, а не подтверждением до успешного CI и испытаний.

## 2026-11-01 — подтверждённые тесты Android 7 и 16

GitHub Actions #41254947669: **API 24 (Android 7) и API 36 (Android 16) прошли все 6 инструментальных тестов и shell smoke.** API 29 и API 33 не прошли только тест `webAppSafeAreaVariablesAndNavigationRender`: тайм-аут обратного вызова `evaluateJavascript`, остальные тесты были успешными. Исправлен тест: каждый опрос берёт актуальный основной Capacitor WebView, ожидает загрузку интерфейса, при разовом тайм-ауте повторяет запрос и не считает сбой успешным результатом. Теперь другой тест проверяет отступ контента относительно реальной верхней системной области, а не допускает `NOT_READY` как успех. На старых Android исправлена несовместимая CSS-функция `min()` в модальных окнах; добавлена безопасная `calc()`-версия. Эти новые изменения требуют повторного запуска CI.

## 01.11.2026 — Критический порядок регистрации Capacitor
В GitHub Actions #41298034157 (commit 7471b13) Android 7 (API24) и Android 16 (API36) действительно показывают WebView, React и нижнюю панель, но тест сообщает `NO_NATIVE_INSETS`. Проверка Java-кода обнаружила, что `registerPlugin(SecureVaultPlugin/NativeAdsPlugin/SystemInsetsPlugin)` выполнялся **после** `super.onCreate`. Для Capacitor 4+ требуется регистрация **до** создания bridge. Исправлено для всех трёх плагинов, также native `getInsets()` теперь читает актуальные root insets и отвечает на первом запуске, даже если первоначальное событие было пропущено. Добавлен блокирующий CI guard на порядок регистрации. Новая сборка/эмуляторы должны подтвердить результат; прежний CI #41298034157 провалился (API29/33 тайм-аут JS, API24/36 NO_NATIVE_INSETS).

## 01.11.2026 — Меню, модальные окна и SDK 37
На небольших и горизонтальных экранах портальные меню не находятся внутри AppShell, поэтому теперь ограничивают ширину/высоту с учётом безопасных областей. Диалоги получают компактную прокручиваемую раскладку при высоте окна до 480px; действия нижней панели и меню имеют безопасные области для касания. Для Android 17 добавлен **отдельный** экспериментальный CI workflow (не замена стабильного APK) с попыткой установить Android SDK 37, выполнить сборку и записать, почему это не получилось. Стабильная ветка выпуска остаётся на SDK 36 до подтверждения.

## 01.11.2026 — Дополнительный контроль системных областей
При первом запуске Android WebView ещё может быть не прикреплён. Теперь метод SystemInsets.getInsets читает WindowInsets у WebView, при их отсутствии — у decor view; если оба источника ещё не готовы, запрашивает системное событие и не выдаёт искусственные нулевые значения за измеренные. JS запрашивает первый снимок сразу, затем повторно после подписки на события. Всплывающие диалоги центрируются внутри доступной области между верхней и нижней системной панелью, кнопка отмены имеет область нажатия минимум 44px, а заголовки учитывают минимальную ширину. Проверка SDK 37 переведена в *ручной экспериментальный запуск*, поскольку прежний job с `continue-on-error` отображался успешным, хотя установка API 37 проваливалась. Невозможность установить SDK 37 больше не будет маскироваться зелёным статусом. Требуется повторное CI.

## 2026-11-01 — Разрешения перед тестом и диагностика тайм-аута
В Android 10 (API29) и Android 13 (API33) instrumentation `evaluateJavascript` периодически не возвращал callback, несмотря на успешную сборку. Добавлен `GrantPermissionRule` с `@Rule(order=0)`: доступ к фото/видео выдаётся тестовым эмуляторам **до** старта Activity. Это предотвращает системный диалог разрешений поверх WebView. На повторном тайм-ауте логируются URL, прогресс загрузки, прикрепление и видимость WebView; тайм-аут остаётся реальной ошибкой теста, а не маскируется успехом. Сценарий смены системной навигации дополнительно фиксирует состояние Android WindowManager. Новая проверка требуется, предыдущий результат API29/33 = не пройдено.

## 2026-11-01 — Измеренные сбои API 29/33 и независимые проверки
В последнем CI APK успешен; эмуляторы API24/API36 успешны, API29/API33 не прошли из-за `CALLBACK_TIMEOUT` WebView. Android 10 logcat показывает `https://localhost/` при прогрессе WebView **10%**, то есть это не доказанный дефект CSS. Теперь сценарий GitHub Actions **не прекращает проверку установленного APK** при отказе Java-инструментации: он независимо устанавливает APK заново, запускает приложение, проверяет узкий/широкий экран, режимы кнопок/жестов и сохраняет по отдельности изображения в артефактах. При любой ошибке хоть одной части весь job остаётся красным; ложного успеха нет. На экстремально маленьких окнах внедрена защита от ситуаций, когда сумма системных отступов превышает размеры видимого WebView. Добавлены соответствующие unit-тесты; требуется повторная сборка.

## 2026-11-01 — Сохранённые кадры эмуляторов и реальные задержки WebView
Анализ артефактов CI #41320275982 подтвердил пустой экран на API29 и корректно отображённый React UI на API36. На API29 WebView доходит до локальной страницы с прогрессом около 10%, но JavaScript callback иногда отсутствует; это не доказанный дефект CSS. Чтобы пользователь не видел бесконечную пустую страницу, Android HTML показывает ошибку и кнопку Retry после 16 секунд отсутствия нижней навигации. В CI теперь включено постоянное питание/разблокировка эмулятора, собираются dumpsys power и состояние Activity, временные NO_NATIVE_INSETS повторно проверяются, но тайм-аут WebView остаётся отказом. Пересчёт безопасных отступов учитывает изменение размеров окна даже без нового значения от Android.
